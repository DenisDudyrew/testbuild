# Отчёт о багах и несоответствиях проекта ZEPHYR (testbuild)

## 🔴 Критические проблемы

### 1. Отсутствие CSP заголовков (XSS уязвимость)
**Файл:** `next.config.ts`, `src/app/layout.tsx`

**Проблема:** Content Security Policy не настроена. Это открывает возможность для XSS-атак через инъекцию вредоносных скриптов.

**Рекомендация:** Добавить CSP заголовки в `next.config.ts` или через middleware:
```typescript
headers: {
  'Content-Security-Policy': "default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; font-src 'self' data:; connect-src 'self' ws: wss:;"
}
```

---

### 2. Некриптографически безопасная генерация кодов верификации
**Файл:** `src/app/api/auth/send-verification/route.ts:30`

**Проблема:** `Math.random()` не является криптографически безопасным. Код верификации может быть предсказуем.

**Текущий код (не исправлен):**
```typescript
const code = Math.floor(100000 + Math.random() * 900000).toString();
```

**Рекомендация:** Использовать `crypto.randomInt()`:
```typescript
const code = crypto.randomInt(100000, 1000000).toString();
```

**Статус:** ❌ Не исправлено

---

### 3. Отсутствие rate limiting на login endpoint
**Файл:** `src/app/api/login/route.ts`

**Проблема:** Endpoint `/api/login` не имеет rate limiting, в отличие от `/api/register`. Это позволяет брутфорс-атаки.

**Текущий код (не исправлен):** В `login/route.ts` нет ни импорта rate-limit, ни проверок.

**Рекомендация:** Добавить rate limiting:
```typescript
import { checkRateLimit, getRateLimitKey, getStrictConfig } from '@/lib/rate-limit';

const rlKey = getRateLimitKey(request, 'login');
const rl = await checkRateLimit(rlKey, getStrictConfig());
if (!rl.success) {
  return NextResponse.json({ error: 'Too many attempts' }, { status: 429 });
}
```

**Статус:** ❌ Не исправлено

---

### 4. Избыточные запросы к БД в JWT callback
**Файл:** `src/auth.ts:36-52`

**Проблема:** При каждом входе делается дополнительный запрос к БД для загрузки `role` и `avatar`. Эти данные уже загружены в `authorize` callback.

**Текущий код (частично оптимизирован):**
```typescript
async jwt({ token, user, trigger }) {
  if (user) {
    token.id = user.id;
    // Загружаем данные из БД только при первом входе
    const dbUser = await prisma.user.findUnique({
      where: { id: user.id },
      select: { role: true, avatar: true },
    });
    // ...
  }
}
```
Запрос к БД всё ещё выполняется при первом входе, хотя `authorize` callback уже имеет эти данные.

**Рекомендация:** Передавать `role` и `avatar` из `authorize` callback через токен:
```typescript
async authorize(credentials) {
  // ...
  return { id: user.id, name: user.username, role: user.role, avatar: user.avatar };
}
```

**Статус:** ⚠️ Частично исправлено (условие `trigger === 'update'` оптимизировано, но начальная загрузка всё ещё делает запрос к БД)

## 🟡 Высокий приоритет

### 6. Отсутствие обработки ошибок в PostForm
**Файл:** `src/components/PostForm.tsx:88-92`

**Проблема:** При ошибке создания поста пользователь не получает уведомление.

**Текущий код (частично исправлен):**
```typescript
} catch (error) {
  console.error("Failed to create post:", error);
} finally {
```
`showAlert` добавлен для ошибок загрузки файла, но для ошибок создания поста — только `console.error`.

**Рекомендация:** Добавить showAlert для ошибки создания поста:
```typescript
} catch (error) {
  console.error("Failed to create post:", error);
  showAlert("Не удалось опубликовать пост");
}
```

**Статус:** ⚠️ Частично исправлено

### 7. Отсутствие rate limiting на API вызовы в Sidebar
**Файл:** `src/components/Sidebar.tsx:93-121`

**Проблема:** Периодические вызовы `/api/users/me`, `/api/notifications`, `/api/messenger/unread` не имеют rate limiting. При большом количестве пользователей это создаст нагрузку.

**Рекомендация:** Добавить client-side throttling или server-side rate limiting.

**Статус:** ❌ Не исправлено

---

### 8. In-memory кэш не работает в multi-instance окружении
**Файл:** `src/lib/cache.ts`

**Проблема:** Кэш хранится в памяти процесса (`MemoryCache`). При горизонтальном масштабировании кэш не будет синхронизирован между инстансами.

**Текущий код (не исправлен):** Используется глобальный `globalThis.__caches` с in-memory Map.

**Рекомендация:** Использовать Redis или аналогичное решение для распределённого кэша.

**Статус:** ❌ Не исправлено

---

### 9. In-memory rate limiter не работает в multi-instance окружении
**Файл:** `src/lib/rate-limit.ts`

**Проблема:** Rate limiter хранит состояние в памяти процесса (`requestCounts` Map). При горизонтальном масштабировании лимиты не будут работать корректно.

**Текущий код (не исправлен):** Используется in-memory `Map<string, { count: number; resetTime: number }>`.

**Рекомендация:** Использовать Upstash Redis (комментарии в коде уже есть) или аналогичное решение.

**Статус:** ❌ Не исправлено

### 15. setInterval на уровне модуля не очищается после тестов
**Файл:** `src/lib/rate-limit.ts:7`

**Проблема:** `setInterval` для очистки старых записей rate-limiter создаётся при импорте модуля:
```typescript
if (typeof process !== 'undefined' && process.env?.NODE_ENV !== 'test') {
  initRateLimitCleanup();
}
```
Хотя есть проверка на `NODE_ENV !== 'test'`, сам интервал не сохраняется для очистки после тестов (хотя `initRateLimitCleanup` возвращает cleanup-функцию).

**Рекомендация:** Убедиться, что cleanup вызывается в `afterAll`/`teardown` тестов.

**Статус:** ⚠️ Частично исправлено (есть защита для тестов, но cleanup не вызывается)
